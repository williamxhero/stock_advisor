# 在内部评测投影器之上使用深模块门面

EvaluationObservatory 对业务调用方只公开评测、预测、实验比较和快照查询，不公开事件重放、水位推进、SQL 投影、资格判定或策略写入。它的内部实现采用不可变执行事件投影器，并以任务周期聚合模型统一 M0/M1/M2、有效窗口、失败分类、工作归因和后验结果。

公开 interface 固定为五类操作：生成评测快照、生成预测快照、评估进化实验、按 ID 读取不可变快照、按范围查询历史摘要。生成操作必须带 `as_of`、请求幂等键和算法或政策版本；结果保存完整输入水位。相同规范化输入返回原快照，新事件、新算法或新政策只能追加新快照。

执行事件不通过 EvaluationObservatory 的公开 interface 记录。实际执行动作的运行时组件、EvidenceGate 和结果核验器继续拥有各自事实，并在自身业务事务中追加规范事件或提供不可变事实适配器。EvaluationObservatory 只读取、校验和引用这些事实。它也不公开 `promote`、`rollback`、`set_schedule`、`set_policy` 或 `mark_qualified`；实验评估只能产生继续观察、淘汰、建议晋升、建议回滚或请求用户选择的证据结论，后续仍由 EvolutionGovernance 裁决并由专属策略服务执行。

采用这一组合而不单独选择三种候选形状中的任何一种：纯事件流 interface 暴露过多重放与水位细节；纯任务周期聚合会弱化跨周期预测、分层实验和迟到事实的表达；由多个 CQRS 窄端口直接组成公共 API 会增加调用方选择负担。门面提供小而稳定的能力集合，内部事件投影器负责可重建性，任务周期模型负责领域一致性，私有读写端口负责测试和存储替换。
