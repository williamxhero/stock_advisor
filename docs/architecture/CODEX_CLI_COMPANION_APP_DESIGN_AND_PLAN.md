# Codex CLI 伴生研判应用：正式设计与实施计划

状态：canonical；2026-08-25 grill 后由用户确认。本文取代旧的“隐藏模型 M0、H0 参与 M1、超时直接揭示 M0”设计。

实现状态：2026-08-25 已完成 Phase A-E 的生产实现与自动化回归。SQLite 是事实源，`data/state/20_COMPANION_MEMORY.md` 是可重建投影；正式 Codex 自动化配置未因伴生链路而修改。

## 1. 产品目标

应用模拟两个专业炒股者之间的长期沟通：AI负责广泛挖掘、独立判断、反证和复盘；用户结合 M0与自己的研究形成 H0；系统再形成独立 M1和伴生 M2。前台始终自然交流，后台负责证据、时点、结构化验证和长期记忆。

最高目标是长期提升真实炒股赚钱能力。手续费、滑点、流动性、回撤和未来信息隔离是“什么才算真实赚钱能力”的后台校验条件，不作为前台口号。

底层原则：

> 只为真正需要认知的步骤付费。

定时触发、投递、状态推进、上下文查找、文件读取、数据库写入、Markdown投影和 UI更新全部由确定性代码完成。LLM只承担搜索理解、判断、反证、自然表达和语义歧义消解。

## 2. 不可妥协的认知契约

### 2.1 M0：客观观察

- M0只讲截至 `as_of` 的客观事实、传播、冲突和真正重要的未知项；
- 不输出看多、看空、买卖、仓位或概率方向；
- 可以引用相关历史 H0及其已验证结果，但必须保留当时对错状态；
- 输出自然口语，不使用大表格和机械化数据报告；
- M0完成后才允许形成 H0。

### 2.2 H0：共享信息后的方向独立判断

- 用户看到 M0，也可以自行搜索，因此 H0不是信息独立，而是方向独立；
- H0是一次提交的消息批次，不是一条文本；
- 原文永久保存，后台只对可识别的市场命题生成判断快照；
- 成交事实、界面反馈、网络问题等仍在 H0原文中，但不强制解释成看多或看空；
- 同一标的、周期和命题以锁定前最后一次明确立场为准，不同标的或周期可以共存；
- H0锁定后永不追加，后续消息都是聊天。

### 2.3 M1：真正盲于 H0 的独立判断

- 只有 H0锁定或明确不评论后才启动；
- 使用全新的 Codex CLI session；
- 输入包不得包含 H0、用户聊天、H0摘要、H0结构化字段或从 H0派生的查询；
- 可以补查 M0之后的新信息，因此必须保存独立 `as_of`；
- 数据与流程满足判断门槛时必须给出明确主立场；观望/不交易也是结论，但不能用含糊两面话逃避；
- 只有关键数据缺失、流程失败、时点污染或未来信息泄露导致不具备资格时，才能发布“不应判断”；
- 正式 M1每轮最多一个且不可覆盖。失败调用记录为 Attempt，不算正式 M1。

### 2.4 M2：伴生综合

- 仅在存在 H0时自动生成；
- 输入冻结为 M0、H0、M1和 M1完成时的证据账本；
- H0锁定后的聊天不进入原始 M2；
- 解释一致、分歧、信息差、周期差和假设差，形成明确综合判断、条件和失效点；
- 只做有目标的深入核对，不重复全量搜索；
- 目标8分钟、硬上限15分钟，优先级低于新任务 M0，可暂停或延后；
- 重要新信息形成 JudgmentRevision，不覆盖 M2。

## 3. 搜索模型

### 3.1 每日证据账本

- 每个交易日盘前只进行一次全量搜索；
- 覆盖新闻、公告/财报、论坛传播、情绪、资金、政策、行业、题材和市场背景；
- 以后所有盘中任务基于账本增量搜索，不重复全量挖掘；
- M1只补查 M0之后的信息、关键反证和尚未覆盖的命题；
- 当日基线缺失时进入 `baseline_recovery`，执行有界恢复并记录真实恢复时间，不能伪装为盘前已知。

### 3.2 时间预算

- 盘前搜索可以更长，但完整盘前链必须在开盘前完成；
- 盘中 M0和 M1的单次联网研究硬上限5分钟；
- M1本地判断目标2分钟、硬上限5分钟；
- 超时必须说明卡在哪一步，不发布不完整正式判断；
- 重试沿用同一冻结输入边界，使用新的 attempt 和 `as_of`。

### 3.3 信息缺失

- 不做“一项缺失、全盘停摆”；
- 普通来源缺失由其余证据补位，后台记录覆盖状态；
- 只有缺失内容直接决定命题是否成立时才阻止方向判断；
- 网络或数据错误确实影响结论时，AI用自然语言说明发生了什么、影响和用户可做的修复；
- 普通覆盖不完美不反复声明，避免合规报告式交流。

### 3.4 传言

传言同时记录事实可靠性和市场传播/价格影响。未经证实不等于低价值；当传播和真实市场响应同时存在时，可以进入可执行判断，但必须使用更小风险边界和更短失效条件。没有市场响应数据时，不基于传言给出执行方向。

## 4. 时间与自动提交

每个 task policy 定义 `m1_publish_deadline`。盘前必须早于开盘；盘中原则上早于下一研判任务。

`h0_auto_submit_at = m1_publish_deadline - m1_reserve`

- `m1_reserve` 初始10分钟，覆盖5分钟硬执行上限、落盘和有限重试；
- 以后可根据设备实际 P90调整，但必须有上下限、版本和回滚；
- 用户可随时提前提交 H0；
- 截止时只自动提交待提交消息；输入框草稿永远不发送；
- 若截止前已开始录音、转写或编辑，给予5分钟宽限，但不能越过 M1最晚发布时间；
- 自动和手动提交使用同一幂等命令；
- 普通聊天待提交批次不自动提交。

当前盘前实现于 08:30 预取公开信息，但 cycle 的正式计划身份仍为 09:00；盘前 M1 最迟 09:29 发布。这样既给全量研究更长窗口，也保证开盘前完成。盘中仍执行5分钟联网硬限制。

## 5. 消息交互

### 5.1 H0前

1. 输入文字或完成 ASR校正；
2. 点击`发送`，文字进入可撤回的待提交区；
3. 可连续发送多条；
4. 点击`提交 H0`，原子锁定全部待提交消息；
5. 没有待提交消息时提交等价于不评论；
6. AI在锁定前不回复，避免影响方向独立性。

### 5.2 H0后

1. `发送`继续向待提交区增加消息；
2. `提交`一次提交整个批次；
3. 一批消息最多触发一次 AI回复；
4. M1运行期间聊天可基于现有证据回复，但新增联网搜索排在 M1之后；
5. 已提交消息不可删除，只能追加修正；
6. 持仓解释、经验记录和聊天回复都以提交边界为准。

## 6. UI

主界面保持三栏：今日列表、AI 消息、我的消息。宽度为固定导航栏加 3:2内容比例。

AI 消息是一条任务级时间线。M0/M1/M2、普通聊天、故障说明和 JudgmentRevision按时间排列；上方使用 M0/M1/M2/最新锚点。每个里程碑独立显示开始和完成时间。朗读选中或最新消息。

我的消息显示待提交和已提交状态。待提交消息有撤回操作；已提交消息只显示原文、时间和必要的持仓处理状态。输入框草稿按 cycle保存。

所有滚动区域复用唯一 `ThinScrollBarStyle`。窗口大小与位置持久化。持仓窗口保持单实例非模态。

WPF 内部 `ScrollViewer` 会用系统滚动条参数覆盖外层样式，因此实现同时固定系统尺寸资源和 `ThinScrollViewerStyle`，并用真实 `ScrollViewer`、`ListBox`、`TextBox` 模板测试2 DIP契约。

## 7. 长期记忆

### 7.1 事实源与检索器

- SQLite不可变事件/文本记录是事实源；
- Markdown/CSV是可重建的人类可读投影；
- 记忆检索通过单一 `MemoryRetriever` interface 提供相关记忆包；
- 初期使用 SQLite FTS、领域标签和时序过滤；
- Memory Palace、向量库或知识图谱未来可作为可重建 adapter接入；
- 新旧检索器必须先回放比较召回、错误关联和未来信息泄露，再切换。

### 7.2 双时间硬契约

所有可进入长期记忆的事实保存 `occurred_at` 与 `known_at`。任何阶段的上下文只允许 `known_at <= stage.as_of`。后来补报的早期成交可以修正当前持仓，但不能回写到当时尚未知的历史判断。

### 7.3 错误也必须记住

所有市场相关 H0和 AI判断都可检索，包括已证明错误的观点。结果状态至少区分未验证、正确、错误、部分正确、方向正确但时机错误、机制正确但结果偶然、已被后续版本取代。检索不能只偏爱赢家，必须召回相似失败和最强反例。

## 8. 判断快照与结果验证

M1、H0和 M2锁定时保存原始口语文本及后台判断快照：标的、方向、周期、参考时点、触发、失效、确信程度和预先选定的比较基准。无法唯一提取的字段标为未声明，不能事后脑补。

次日统一做早期检查，但只有到声明周期结束或失效条件触发后才结案。评价包括绝对收益、相对大盘/行业/题材的表现、最大有利/不利波动、时机、机制和风险控制。后台评测不在主界面展示排行榜，只在真正有用时以自然语言带回对话。

## 9. 持仓

- AI只给建议，用户拥有全部实际操作权；
- 只有明确已经成交或当前真实状态的用户陈述才进入解释；
- 计划、建议、条件句、歧义或缺字段不得更新事实持仓；
- 完整草案由确定性校验事务提交，一条消息多笔成交必须全部通过才原子提交；
- 持仓按用户最后同步事实计算，只有过期会显著影响精确建议时才自然询问；
- 发生时间和同步时间分别保存；
- 撤销写反向事件，不删除历史；
- LLM不下单、不连接券商、不从行情反推用户成交。

## 10. ASR

- 录音时输入框显示实时音量波形；
- Recording/Transcribing期间输入、发送和提交禁用；
- 录音归属开始时的 cycle，切换任务不会串稿；
- 转写以换行追加到原草稿，不覆盖；
- 股票名称、代码、题材和当前上下文形成本地热词/纠错上下文；
- 用户检查并点击发送、提交后才产生业务事件。

## 11. 安全最小边界

不建设复杂的多层内容安全流水线，只保留关键权限隔离：

- 联网研究调用只获得公开标的、主题、时点和搜索目标，不读取用户私人消息或本地资料；
- 本地判断调用获得只读证据包和最小必要本地上下文，不具备联网或外传能力；
- 网页内容可影响认知，但不能获得本地读取、写入、执行或外传权限；
- 模型不直接修改数据库、Markdown、自动化、代码或工作流；只返回提案。

## 12. 内部多视角与自然表达

对外保持一个稳定第一人称炒股搭档，不伪造真实持仓、交易或情绪。对内固定使用少量差异明显的视角：

- 交易者：价量、资金、情绪、龙头与传播；
- 产业投资者：业务、盈利、估值、政策和周期；
- 怀疑者：反证、拥挤、流动性、幸存者偏差、叙事和未来泄露。

视角不投票、不强制共识。高风险、高冲突、真实操作或传言临界场景才增加独立反证调用；普通场景在一次判断调用内完成多视角碰撞。

## 13. 应用进化

AI可以提出或更新经验、查询模板、搜索顺序、反证习惯和方法权重。边界为：

- 运行故障立即重试、降级或提示，不等多次验证；
- 明确的确定性流程缺陷可在测试后修正文档/配置；
- 投资方法和权重变化必须经过重复证据或历史回放，防止单次过拟合；
- AI不得生成或自动启用代码、工具、权限、自动化或安全规则；
- 新 LLM步骤必须证明不能由确定性代码解决，并通过对照评测证明收益；
- 增加调用预算、搜索范围或并发必须由用户批准并可回退。

## 14. 深 module 与 interface

### `CompanionCycle`

外部 interface 只接受版本化命令并返回 cycle projection。其 implementation负责 H0批次、截止、M1 attempt、M2、幂等、不可变 artifact和事件 outbox。UI不理解状态迁移细节。

### `ContextAssembler`

外部 interface 为 `assemble(stage, cycle_id, as_of) -> StagePacket`。其 implementation负责双时间过滤、每日账本、相关记忆、隐私裁剪、H0盲区和调用预算。任何 LLM调用都不得自行遍历项目文件。

### `CompanionWorkspace`

外部 interface 为 `project(events, cycle_id) -> WorkspaceProjection`。其 implementation负责把事件投影为任务级 AI时间线、我的消息、待提交状态、按钮状态、倒计时和持仓处理状态。

### `MemoryRetriever`

外部 interface 为 `retrieve(query, known_at) -> MemoryBundle`。SQLite FTS为首个生产 adapter，内存 fake用于测试；未来检索技术通过同一 seam替换。

## 15. 默认 LLM调用预算

一个完整、有 H0 的周期默认最多包含：

1. M0联网研究；
2. M0本地表达与记忆融合；
3. M1最新信息补查；
4. M1独立本地判断；
5. M2本地综合。

无 H0跳过 M2。普通聊天按每个提交批次一次调用；只有确实需要新信息时才追加联网研究。持仓优先规则解析，歧义时复用聊天或一次短调用。任何额外阶段必须经过用户批准。

默认按认知成本分级：公开全量/增量检索使用 `gpt-5.6-terra`，M1/M2和反思等真正方向判断使用 `gpt-5.6-sol`，M0口语化整理、普通聊天和持仓解释使用 `gpt-5.6-luna`；三类均可通过本地环境变量覆盖。显式指定模型也是运行契约的一部分，避免依赖可能过期的 Codex 默认模型缓存。

联网 packet 只能包含公开研究范围。M1增量检索必须继承 M0公开证据的摘要、来源标题、已知缺口和检索起点，并始终带上当时段的 A 股指数、广度、量价、公告财报、政策、论坛传播、资金和领涨/领跌扫描问题；不得因为隔离本地持仓而退化成“没有研究对象”。

LLM attempt 的原始异常只进入本地审计。UI事件只能携带归类后的诊断码和自然语言影响；重试成功后旧故障卡折叠，最终 M1/M2及其真实开始/完成时间继续保留。

## 16. 状态模型

主路径：

```text
scheduled -> queued -> researching_m0 -> awaiting_h0
awaiting_h0 -> h0_locked -> researching_m1 -> judging_m1 -> m1_ready
m1_ready + has_h0 -> synthesizing_m2 -> complete
m1_ready + no_h0 -> complete
```

辅助状态：`voice_grace`、`m1_retry_wait`、`m2_deferred`、`waiting_for_repair`、`failed`、`missed`。正式 artifact与 attempt分开；重试不创建第二份正式 M1。

## 17. 数据增量

现有 SQLite在兼容迁移中增加：

- cycle：`m1_publish_deadline`、`h0_auto_submit_at`、`h0_locked_at`、`h0_artifact_id`、`m1_started_at`、`m1_completed_at`、`m2_started_at`、`m2_completed_at`；
- `message_batch`与`message_item`：待提交、撤回、已提交和 H0归属；
- `llm_attempt`：stage、attempt、时间、status、error、input/output hash、as_of；
- `evidence_ledger_entry`：source、occurred_at、known_at、自然语言内容和覆盖状态；
- `judgment_snapshot`与`outcome_checkpoint`；
- `memory_index_entry`：事实 artifact到可重建检索索引的映射。

交换合同增加命令：`stage_message`、`withdraw_staged_message`、`commit_h0`、`commit_chat_batch`、`request_projection`。事件增加：`message.staged`、`message.withdrawn`、`h0.locked`、`m1.started/ready/failed`、`m2.started/ready/deferred`、`chat.ready`和`judgment.revised`。

## 18. 实施阶段与 Gate

### Phase A：canonical 设计与兼容迁移

- 更新领域词汇、UI名称、合同和 schema；
- 添加兼容数据库迁移；
- 旧 cycle保持只读可投影，不伪造新 M2；
- 新状态机通过 fake clock和幂等测试。

Gate：旧数据库可打开；旧测试保留；新 H0批次和自动提交测试通过。

### Phase B：新 runtime

- 实现 CompanionCycle深 module；
- 实现 StagePacket上下文组装，彻底移除逐层 prompt读取；
- 拆分联网研究与本地判断 adapter；
- 实现 M1盲输入测试和一个正式 M1约束；
- 实现可延后 M2和聊天优先级；
- 增加调用预算审计。

Gate：测试证明 M1 packet没有 H0派生内容；时间预算、重试、抢占和恢复通过。

### Phase C：任务级时间线 UI

- 用统一 AI时间线替换固定 M0/M1区块；
- 实现锚点、选择朗读、无强制滚动；
- 将“我的判断”改为“我的消息”；
- 实现发送/提交 H0/提交、待提交撤回和任务独立草稿；
- 接入 ASR、持仓状态和自动提交倒计时。

Gate：切换任务不串消息；H0前无 AI回复；输入框草稿不自动提交；M1只显示一次。

### Phase D：记忆、快照与结果

- 实现双时间事实和 SQLite FTS检索 adapter；
- 实现判断快照、阶段检查和 Outcome；
