# A股实盘决策系统

## 目标
建立一个可持续积累、验证和修正的个人A股交易决策系统，而不是只保存零散聊天结论。

本系统的交易风格定位为：

> **以龙头视角管理全部股票，以事件和市场叙事发现机会，以资金与情绪判断生命周期，以股票在题材中的地位决定买入、持有、加仓、减仓和清仓。**

这不是传统技术指标系统，也不是黑箱量化排名系统。价格、成交、换手、涨停结构等只用于观察参与者行为、承接、扩散、拥挤和Price Reaction Surprise，不能脱离事件、题材与股票角色成为独立交易理由。

新股票发现与现有持仓管理必须使用同一套逻辑，不得出现“候选股按事件情绪选择、持仓股却按均线指标处理”的双轨体系。

系统遵循四层结构：

1. **当前状态（Current State）**：唯一最新持仓、成本、总资产、最近交易。
2. **交易规则（Playbook）**：已经经过反复讨论或验证、可用于未来决策的稳定规则。
3. **案例库（Casebook）**：保留真实交易案例、当时判断、实际操作与后续结果，防止只记结论不记背景。
4. **决策日志（Decision Log）**：记录每一次关键建议与结果，用数据检验9:45、10:30、14:30判断是否真正有效。

另设 **待验证假说（Hypotheses）**，避免把一次经验直接升级成永久规则。

## 系统执行架构

本系统采用五层分工，避免同一规则同时散落在Schedule、聊天和文件中：

1. **Codex Automation（极薄触发器）**：只定义何时运行，并引用一个本地 dispatcher prompt 文件；不保存时点分发、`task_key`或业务规则。
2. **Dispatcher Prompt（时点分发层）**：保存在`automations/prompts/`，把当前触发时点解析成唯一`task_key`，并处理组合调度产生的无效时点。
3. **Schedule Registry（任务注册与公共运行层）**：统一保存`task_key → Protocol文件/章节`路由、任务名称、交易日策略、异常边界和结果投递策略。
4. **Protocol（执行协议）**：定义每次任务具体读取什么、如何分析、如何输出、允许写入哪些文件。
5. **Guide / Playbook / Portfolio / Casebook / Hypotheses / Log（原则、规则、事实与证据）**：分别保存系统架构、稳定规则、当前状态、案例、待验证观点和历史决策结果。

当前正式协议：

- `docs/protocols/07_DAILY_EXECUTION_PROTOCOL.md`：09:45、10:30、14:30、15:20的每日执行逻辑。
- `docs/protocols/08_PERIODIC_REVIEW_PROTOCOL.md`：月度、季度、年度的统计复盘与规则维护逻辑。
- `docs/protocols/09_OPPORTUNITY_DISCOVERY_PROTOCOL.md`：全市场事件、题材生命周期、股票角色与新机会发现逻辑。

当前统一任务注册表：

- `automations/14_SCHEDULE_REGISTRY.md`：全部本Project Schedule的唯一注册、路由、公共异常处理与结果投递入口。

新增分析状态与审计文件：

- `data/state/10_THEME_STATE.csv`：题材生命周期与状态迁移的当前分析状态；
- `data/state/11_STOCK_STATE.csv`：持仓、最近卖出与候选股票的题材角色、龙头地位和失效条件；
- `data/logs/12_OPPORTUNITY_LOG.csv`：全市场机会的发现、入选、淘汰与T+N结果；
- `docs/governance/13_DATA_SEMANTICS.md`：事件、资金、情绪、注意力、拥挤度和数据置信度的统一口径。

### 配置优先级与异常处理

- Codex自动化不得复制dispatcher、Registry或Protocol中的时点分发、业务、读写、交易日、异常和投递逻辑；规则更新应修改项目内的对应文件。
- Dispatcher必须通过`automations/14_SCHEDULE_REGISTRY.md`中的唯一`task_key`解析当前Protocol入口；Dispatcher、Registry或Protocol缺失、无法读取、版本不明、文件身份不明或写入冲突时，应报告异常并停止，不得自行用历史Schedule长Prompt或聊天记忆代替。
- 若Protocol与本Guide或Trading Playbook冲突，以本Guide和Trading Playbook中的高层边界与正式规则为准，并记录冲突，等待人工修订Protocol。

### 版本与可审计性

- Protocol顶部必须保存版本号、更新日期和Change Log。
- 每条新盘中决策都必须在`data/logs/05_DECISION_LOG.csv`记录实际使用的`protocol_version`。
- 协议升级后只影响新样本；不得回写或重标历史样本的协议版本。
- 周期复盘报告必须记录所使用的周期复盘协议版本，并允许比较不同Daily Execution Protocol版本的效果。

## 信息优先级

### 事实来源优先级

当不同来源发生冲突时，严格按以下顺序取值：

1. **用户最新明确报告的实际成交信息**；
2. **`data/portfolio/01_CURRENT_PORTFOLIO.md` 中的当前持仓事实**；
3. **本 Project 其他文件与历史记录**；
4. **普通 Memory 或其他聊天中的旧信息**。

不得用低优先级信息覆盖高优先级事实。用户明确报告成交后，应立即原地更新 `data/portfolio/01_CURRENT_PORTFOLIO.md`，使后续定时任务直接读取到最新持仓。

### 龙头视角的统一分析链

任何新股票或持仓股的正式判断必须沿同一条证据链展开：

> 市场情绪与风险偏好 → 当前主线/新增事件 → 题材生命周期 → 股票角色与地位变化 → 资金、扩散与价格反应 → 下一批潜在买方 → 组合适配 → 操作与失效条件

最小分析单位是：

> `Event × Theme × Stock Role × Lifecycle State`

股票角色统一使用：市场总龙头、题材龙头、容量核心、直接受益核心、扩散承接者、普通跟随、擦边/FOMO。没有明确因果关系和角色定位的股票，不得仅因“还没涨”“成交放大”或技术形态进入正式买入候选。

### 分析维度优先级

每天判断优先使用：

1. 市场情绪、风险偏好与主线强度；
2. 事件质量、叙事新颖性与因果传导；
3. 题材生命周期与扩散/退潮状态；
4. 资金行为、承接、吸收与价格冲击；
5. 股票在题材中的角色和龙头地位变化；
6. 拥挤度、注意力边际效率与潜在卖方供给；
7. Price Reaction Surprise（理论预期与真实反应的偏差）；
8. 相对题材、板块与指数强弱；
9. 传统技术指标仅作为辅助证据，禁止独立触发交易。

核心问题不是“股票涨还是跌”，而是：

> 在当时背景下，它理论上应该多强/多弱？实际价格行为是否超预期？

## 三个固定盘中决策时点

### 09:45 — 异常发现
开盘15分钟后，重点观察：
- 隔夜或早盘新增事件是否形成新主线；
- 题材龙头、容量核心和后排扩散是否符合理论预期；
- 集合竞价与开盘缺口是否被接受；
- 高开后是承接还是兑现；
- 低开后是否快速收回；
- 是否出现明显强于/弱于板块的异常；
- 最近1—2日刚卖出的股票是否出现反包/重新定价迹象。

原则：**发现异常，不急于把15分钟走势定义为全天趋势。**

### 10:30 — 趋势确认
开盘一小时后，重点确认：
- 早盘点火是否真正进入扩散，还是假点火/冲高兑现；
- 分歧后资金优先回流哪只核心股票；
- 持仓或候选股的题材角色是否升级、维持或下降；
- 09:45的强弱是否持续；
- 第一轮获利盘/割肉盘释放后是否仍有资金承接；
- 高开强势是否守住；
- 低开修复是否持续；
- 是否值得真正提高/降低组合风险敞口。

原则：**确认后再提高操作强度。**

### 14:30 — 收盘 + 次日/未来决策
不能只判断当天剩余30分钟，必须同时比较：
- 当天真正形成的主线、题材生命周期与核心股票；
- 新开仓、原持仓加减仓、弱换强和继续持有现金之间的优先级；
- 今天卖出后，明天高开、反包、突然拉升的机会成本；
- 今天持有后，明天低开、补跌、事件兑现的隔夜风险；
- 未来1—3个交易日的基准/偏强/偏弱路径；
- 未来1—2周已知财报、会议、政策、解禁、减持、商品价格与外围事件；
- 当前操作的风险收益是否对称。

原则：**任何清仓建议都必须附带“如果明天走势相反怎么办”的预案。**

## 仓位管理

所有个股判断必须同时纳入组合仓位管理：
- 给出建议总股票仓位；
- 给出每只持仓目标仓位区间；
- 给出具体加减股数/金额；
- 计算操作后的总仓位和现金比例；
- 避免多个高Beta、同题材股票同时重仓；
- 对最小交易单位造成“全留/全卖”的仓位，必须显式提高决策阈值。

仓位变化不得由技术指标或成本盈亏直接决定。加仓应对应事件逻辑、题材状态或龙头地位的确定性提高；减仓/清仓应对应叙事、资金或地位的实质弱化。点火试错仓、扩散加仓、拥挤不新开仓等比例属于待验证假说，具体数值保存在`docs/research/04_HYPOTHESES.md`，未经验证不得伪装成正式规则。

## 经验晋级机制

### Level 0 — 观察
只出现一次，记录案例，不形成规则。

### Level 1 — 假说
类似情况重复出现2—3次，进入待验证假说库。

### Level 2 — 经验
出现5—10次，逻辑与结果较一致，可以进入经验层。

### Level 3 — 规则候选
需要统计检验、样本外或至少跨市场环境验证。

### Level 4 — 正式Playbook规则
证据充分后，才进入默认决策流程。

**禁止因为一次卖飞/一次成功，就立刻形成永久规则。**

## 每日维护流程

1. 用户发生买入/卖出后，先更新 `data/portfolio/01_CURRENT_PORTFOLIO.md`。
2. 每次9:45 / 10:30 / 14:30的重要判断，连同实际使用的`protocol_version`记录到 `data/logs/05_DECISION_LOG.csv`。
3. 收盘后选择真正有信息价值的事件写入 `docs/research/03_CASEBOOK.md`。
4. 新观点先写入 `docs/research/04_HYPOTHESES.md`，不要直接写入Playbook。
5. 定期回看T+1、T+3、T+5结果，把假说升级、降级或删除。
6. 15:20更新当日持仓与重点股票的角色/生命周期证据；每个A股交易日09:00由机会发现任务按`docs/protocols/09_OPPORTUNITY_DISCOVERY_PROTOCOL.md`吸收前一交易日收盘、晚间公告、隔夜外围与当日清晨信息，更新题材状态和当日盘前候选池。
7. 新候选、候选淘汰和弱换强决策必须写入`data/logs/12_OPPORTUNITY_LOG.csv`，不得只停留在聊天中。

## 文件权限与写入边界

### `data/portfolio/01_CURRENT_PORTFOLIO.md` — 事实层
- 只有用户明确报告已发生的真实成交、持股数量变化或资产变化时才能修改；
- “建议买入/卖出”“计划成交”“条件触发后操作”均不属于成交事实；
- 定时任务不得依据自己的操作建议推定成交，更不得自动改变持仓；
- 若无法确认是否成交，保持原文件不变并向用户询问。

### `data/logs/05_DECISION_LOG.csv` — 审计层
- 每次09:45、10:30、14:30的正式判断都应原地追加记录；
- `advice` / `shares_advised` 记录建议，`actual_action` / `shares_actual` / `position_after` 只有在真实成交已确认时填写；
- 未确认成交时，实际操作字段留空，不得把建议写成事实；
- 收盘复盘负责补齐收盘信息及T+1/T+3/T+5结果。

### `docs/research/03_CASEBOOK.md` — 案例层
- 只追加真正具有学习价值、能够检验或改变认知的交易案例；
- 不记录普通涨跌，不为了“每天有内容”而强行追加。

### `docs/research/04_HYPOTHESES.md` — 研究层
- 新观点先作为待验证假说积累支持证据与反证；
- 每条假说应记录验证指标和当前等级，不得因单次案例直接升级为规则。

### `docs/strategy/02_TRADING_PLAYBOOK.md` — 规则层
- 最谨慎修改；日常定时任务默认只读；
- 只有经过足够案例、T+N跟踪或统计检验后，才可升级、降级或删除规则；
- 规则修改必须说明证据与理由。

### `docs/governance/00_PROJECT_GUIDE.md` — 系统架构层
- 极少修改；仅在系统流程、优先级或文件职责发生稳定变化时更新。

### `docs/templates/06_DAILY_REVIEW_TEMPLATE.md` — 模板层
- 作为15:20收盘复盘的输出结构；仅在复盘流程发生稳定变化时修改。

### `data/state/10_THEME_STATE.csv` / `data/state/11_STOCK_STATE.csv` — 分析状态层
- 保存当前题材生命周期、股票角色、龙头地位、下一批潜在买方与失效条件；
- 它们是可更新的分析判断，不是持仓成交事实，不得反向覆盖`data/portfolio/01_CURRENT_PORTFOLIO.md`；
- 每次状态变化必须带时间、证据和协议版本，不得无痕改写。

### `data/logs/12_OPPORTUNITY_LOG.csv` — 机会审计层
- 记录发现、观察、入选、淘汰、新开仓建议、弱换强及其T+N结果；
- 被拒绝的机会也应保留关键拒绝原因，以避免只统计成功候选；
- 不得把候选或建议写成真实成交。

### `docs/governance/13_DATA_SEMANTICS.md` — 口径层
- 所有任务必须遵守其中的数据定义和置信度边界；
- 没有可观察证据时不得把供应商“主力净流入”直接表述为机构资金；
- 口径发生变化时只影响新样本，不重写历史判断。

## 定时任务统一约束

- 每个本Project Codex自动化必须是极薄触发器，只保留本地项目根目录、一个`automations/prompts/*.md`入口、入口不可读时停止并报告。不得保留其他规则。
- 自动化prompt中禁止出现时点分发、`task_key`、业务规则、文件清单、交易日判断、异常处理、输出格式或写入规则。
- `automations/prompts/`是时点分发的Single Source of Truth；`automations/14_SCHEDULE_REGISTRY.md`是任务路由、公共运行边界和结果投递策略的Single Source of Truth。
- 新增、删除、改名或迁移任务时，先修改dispatcher，再按需修改Registry和Protocol，最后更新Codex本地自动化；完成后运行`scripts/validate_automations.ps1 -CheckInstalled`。
- Registry按`task_key`解析当前Protocol及精确章节：每日任务使用`docs/protocols/07_DAILY_EXECUTION_PROTOCOL.md`，周期复盘使用`docs/protocols/08_PERIODIC_REVIEW_PROTOCOL.md`，全市场机会发现使用`docs/protocols/09_OPPORTUNITY_DISCOVERY_PROTOCOL.md`。
- 具体读取、分析、输出和文件写入规则继续由对应Protocol定义；Registry不得复制业务分析逻辑。
- 09:00负责形成当日盘前观察池与理论预期，不直接把候选写成买入指令；09:45负责用集合竞价和开盘15分钟的真实资金反应验证、升级或淘汰候选。
- 09:45负责发现异常；10:30负责确认异常是否持续；14:30负责今日操作与未来1—3个交易日路径，三者不得重复做同一种分析。
- 15:20负责收盘复盘、日志补全、T+N验证以及有条件的知识沉淀，不负责发出当日交易指令。
- 交易日策略和结果投递策略由Registry统一配置；具体跳过行为及可否写入由对应Protocol执行。
- 任何文件写入都必须原地更新对应文件，不创建同名副本。
- Dispatcher、Registry或Protocol缺失、无法读取、版本冲突或写入失败时必须报告异常，不得回退到旧Schedule业务逻辑、聊天历史、Memory或归档内容。
