# `stock_advisor` 通用 AI 知识运行时完整设计

## 0. 本文用途

本文是 `stock_advisor` 项目“通用 AI 知识运行时”的完整设计规格。

接手项目的 AI 不需要阅读此前聊天记录。应以本文作为当前架构目标，并结合现有代码库逐步实施。

核心任务不是建设一个固定的“股票题材图谱”，而是：

> 建立一套由 AI 理解新领域、提出知识结构和知识变化，由本地确定性 Runtime 负责验证、治理、提交、追踪和历史重建的通用知识运行时。

它最终应支持：

- 题材、子题材、股票及角色；
- 产业链；
- 供应链；
- 资金链；
- 事件传播链；
- 政策影响链；
- 机构、产品、人物等其他领域；
- AI 后续自行发现的新知识领域。

增加新领域时，原则上**不需要新增业务表、不需要新增专用业务模块，也不允许 AI 修改物理数据库 Schema**。

------

# 1. 项目现状与不可破坏的基础

当前系统已经存在：

- SQLite 运行数据库；
- Evidence Ledger；
- `memory_proposition`；
- `knowledge_change_proposal`；
- 结构化 ProviderBroker；
- M0 / M1 / M2 阶段；
- 冻结证据；
- 审计记录；
- Runtime 作为唯一业务写入者；
- 本地 Web Access Gateway。

这些基础继续保留，不整体替换。

整个应用仍然遵守：

> 本地桌面应用、单机运行、尽可能不增加独立网络服务。

`KnowledgeService` 应作为当前 Runtime 内部的深模块，而不是另外启动一个 AI 服务或微服务。现有设计同样明确：SQLite 可以继续作为权威存储，知识治理层本身仍然需要存在。

------

# 2. 最重要的架构原则

整个系统必须遵守下面八个原则。

## 2.1 ChangeSet 日志是真正权威源

正式知识修改首先形成：

```
KnowledgeChangeSet
```

经过验证和治理后提交到：

```
SQLite Append-only Change Log
```

任何实体表、Statement 表、图数据库、搜索索引都只是由 ChangeSet 重建出来的投影。

因此：

> 权威知识不能只存在于图数据库里。

图数据库损坏、删除或者将来更换技术以后，必须能够从 SQLite ChangeSet 完整重建。

------

## 2.2 核心知识对象不是 Graph Edge，而是 Statement

不要把系统设计成：

```
Entity + Relation + Observation
```

三套彼此独立的知识模型。

统一使用：

> ```
> Entity + Statement
> ```

图中的 Relation 只是 Statement 的一种投影。

Observation 同样是一种带时间、值和上下文的 Statement。

这样以后 AI 创建新的知识领域时，不需要判断：

> “这个东西到底应该建成关系表还是 Observation 表？”

全部统一表示。

------

## 2.3 Graph 只是知识的一种查询投影

核心层不依赖：

- Cypher；
- Neo4j；
- LadybugDB；
- SQL/PGQ；
- 某个具体图引擎。

KnowledgeService 接收统一 QuerySpec。

底层 Adapter 再把 QuerySpec 编译为具体数据库查询。

因此未来更换图引擎：

> 不应该影响 AI 协议、Ontology、Statement、Evidence、M0/M1/M2 或治理系统。

------

## 2.4 原始行情不是知识

分钟行情、Tick、L2、订单流、资金流数值、连续排名等高频数据不能全部进入知识图谱。

应该分成：

```text
Raw Market Data
      ↓
Feature Store
      ↓
Detector / AI
      ↓
Semantic Statement
      ↓
KnowledgeService
```

例如不要保存：

```text
10:01 题材强度 0.72
10:02 题材强度 0.74
10:03 题材强度 0.76
...
```

知识层应该保存语义变化：

```text
10:03—10:47
AI Hardware 题材进入 strengthening 状态
confidence = 0.91
```

原始数值仍保存在行情/特征系统。

KnowledgeService 管的是：

> 有意义的语义状态、事实、关系、解释、假设、预测和知识变化。

------

## 2.5 AI负责语义，Runtime负责治理

边界必须始终清楚：

```text
AI
理解
推理
发现关系
提出 Schema
提出 Statement
提出修正
提出假设

        ↓

KnowledgeService
Schema 验证
权限验证
Evidence 验证
实体消歧
重复检测
冲突检测
时态检查
审批策略
提交
版本
索引
追踪
回滚
```

KnowledgeService 本身不是另一个 LLM。

它是确定性程序。

AI 可以认为：

> “股票 A 正在从板块跟风股升级为核心。”

KnowledgeService 不判断这个结论聪不聪明。

它检查：

- 谁提出的；
- 根据什么 Evidence；
- 属于事实、分类、因果还是预测；
- confidence；
- 有效期；
- 是否与已有 Statement 冲突；
- 是否允许自动写入；
- 是否需要复核；
- 是否应该隔离。

AI 永远不能直接执行 SQL、Cypher、DDL 或任意代码修改知识库。现有设计已经明确要求这一安全边界。

------

## 2.6 所有修改追加式完成

禁止：

```text
覆盖旧知识
删除旧判断
修改历史
```

正确方式：

```text
旧 Statement
    ↓
superseded / expired / rejected
    ↓
新 Statement
```

或者：

```text
ChangeSet 100
    ↓
ChangeSet 137 对其进行补偿
```

历史必须能够回答：

> 2026-08-10 当时系统知道什么？

以及：

> 2026-08-20 为什么推翻了当时的判断？

------

## 2.7 正式研判必须完全可重复

任何正式 M0/M1/M2 运行都必须绑定一个确定的：

```
KnowledgeSnapshot
```

必须能够证明：

> GPT 与 Claude 在 M1 中看到的是完全相同的数据。

不是“大概相同”。

而是：

```text
snapshot_hash
=
同一个 SHA-256
```

------

## 2.8 SQLite-first，Graph-engine-ready

第一阶段不要预先锁死 LadybugDB。

架构应支持：

```text
QuerySpec
    ↓
GraphQueryAdapter
    ├── SQLiteGraphAdapter
    └── LadybugGraphAdapter
```

V1 默认：

> SQLite。

通过真实 benchmark 证明 SQLite 已经成为图查询瓶颈以后，再启用 LadybugDB。

因此最终原则是：

> LadybugDB 是一种可能的 GraphProjection 实现，而不是整个知识架构的一部分。

# 4. 核心概念：Entity

Entity 表示具有稳定身份的对象。

例如：

```text
股票
公司
题材
子题材
产业环节
产品
机构
事件
政策
地区
资金池
人物
指数
ETF
```

Entity 至少包含：

```text
entity_id
type_id
canonical_name
lifecycle_state
created_seq
retired_seq
```

另外维护：

```text
entity_alias
entity_identity
```

------

# 5. Entity Identity 与消歧

同一个现实对象可能存在：

```text
宁德时代
CATL
300750
300750.SZ
```

它们不能变成四个 Entity。

因此需要：

```
EntityResolver
```

身份信息分开保存：

```text
namespace = stock_code
value     = 300750.SZ

namespace = company_name
value     = 宁德时代

namespace = english_name
value     = CATL
```

AI 可以提出：

```text
possible_duplicate
```

但：

> Entity Merge 属于高风险操作。

默认必须人工确认。

实体合并不能真正删除旧 Entity ID。

应该形成：

```text
entity A
entity B
   ↓
merged_into
   ↓
entity C
```

并继续支持历史 ID 解析。

------

# 6. 核心概念：Statement

所有正式知识统一表示成 Statement。

Statement 可以表示：

- 事实；
- 分类；
- 关系；
- Observation；
- 因果解释；
- 状态；
- 排名；
- 假设；
- 预测；
- 多实体关系。

例如：

```text
Stock A LEADS Theme B
```

表示成：

```json
{
  "predicate": "leads",
  "arguments": [
    {
      "role": "stock",
      "entity_id": "stock:A"
    },
    {
      "role": "theme",
      "entity_id": "theme:B"
    }
  ]
}
```

------

# 7. Statement 支持 N 元关系

不能只允许：

```
subject → predicate → object
```

因为未来很多知识不是简单二元关系。

例如：

> 某资金池在 10:30—11:00 通过 ETF 流向机器人题材约 3 亿元。

可以表示：

```text
predicate:
capital_flow

arguments:
source       = CapitalPool A
destination  = Theme Robotics
channel      = ETF
amount       = 300,000,000
currency     = CNY
```

因此：

```
statement_argument
```

必须允许：

```text
entity
string
integer
float
decimal
boolean
datetime
duration
enum
JSON typed value
```

PredicateDefinition 决定各 role 的类型要求。

------

# 8. Statement 的五个不同维度

不要再只用：

```text
asserted
derived
hypothesis
```

描述全部知识性质。

至少分成五个独立维度。

------

## 8.1 claim_nature

表示“这句话是什么性质”。

```text
observed
reported
classificatory
causal
predictive
```

含义：

### observed

系统直接观察到的数据事实。

例如：

> 10:30 某 ETF 成交额达到某值。

### reported

来自公告、新闻、研报或第三方的信息。

例如：

> 公司公告某项目已经投产。

### classificatory

分类和角色判断。

例如：

> 股票 A 属于液冷题材。

> 股票 A 当前是板块核心。

### causal

因果解释。

例如：

> 某政策可能通过资本开支增加利好数据中心设备商。

### predictive

未来预测。

例如：

> 资金可能由机器人题材轮动到券商。

------

## 8.2 epistemic_class

表示知识来源层级：

```text
evidence_backed
derived
hypothesis
```

### evidence_backed

有直接 Evidence 支持。

### derived

确定性规则或明确算法从其他 Statement 推导。

### hypothesis

AI 或算法发现的候选关系。

------

## 8.3 origin_kind

表示是谁/什么机制产生：

```text
user_input
evidence_extraction
deterministic_rule
algorithm
ai_judgment
migration
```

------

## 8.4 governance_state

表示治理状态：

```text
proposed
active
rejected
expired
superseded
quarantined
```

------

## 8.5 confidence

至少保存：

```text
model_confidence
effective_confidence
```

不能把 AI 自己输出的：

```text
confidence = 0.93
```

直接解释为真实 93% 概率。

`model_confidence` 只是模型自己的判断。

正式查询和治理优先使用：

```
effective_confidence
```

------

# 9. Effective Confidence

由 Runtime 计算。

可以综合：

```text
Evidence quality
Source reliability
Evidence agreement
Extraction confidence
Model calibration
Rule reliability
Freshness
Contradicting evidence
Historical accuracy
```

不要把初始公式设计成无法修改的硬编码数学真理。

应该做成：

```
ConfidencePolicy
```

例如：

```text
policy_version = confidence_v1
```

所有 effective confidence 都能追溯到计算策略版本。

------

# 10. EvidenceBinding

Statement 不能只是保存：

```text
evidence_ids[]
```

应该建立：

```
EvidenceBinding
```

结构例如：

```text
statement_id
evidence_id

stance:
  supports
  contradicts
  contextual

strength
locator
extracted_span
evidence_time
binding_method
```

于是可以回答：

> 哪些 Evidence 支持这条 Statement？

也可以回答：

> 哪些 Evidence 与它冲突？

------

# 11. 双时态模型

所有正式 Statement 必须支持双时态。

第一套时间：

```text
valid_from
valid_to
```

表示：

> 现实中它什么时候成立？

第二套时间：

```text
system_from
system_to
```

表示：

> 系统什么时候知道或者接受这件事？

例如：

公司 A 从：

```text
2026-08-01
```

开始供应公司 B。

系统直到：

```text
2026-08-12
```

才得到可靠 Evidence。

则：

```text
valid_from  = 2026-08-01
system_from = 2026-08-12
```

执行 8 月 10 日的历史回测时：

> 必须看不到这条知识。

否则产生未来数据泄漏。

------

# 12. knowledge_seq

每次正式 ChangeSet 成功提交以后：

```text
knowledge_seq += 1
```

它是系统全局单调递增的知识版本。

例如：

```text
KnowledgeSnapshot@184320
```

表示：

> 截止 seq 184320 的全部已提交知识。

它比单独依赖 wall-clock 时间更适合：

- 可重复实验；
- M1 duel；
- 历史回测；
- 错误复现；
- projection 一致性；
- 审计。

------

# 13. Ontology

AI 允许创建逻辑 Ontology。

Ontology 至少包含：

```text
EntityTypeDefinition
PredicateDefinition
RuleDefinition
ViewDefinition
ProcedureDefinition
```

AI 创建的是：

> 逻辑 Schema。

不是：

> SQLite DDL。

AI 永远不能：

```text
CREATE TABLE
ALTER TABLE
CREATE INDEX
```

物理结构全部由 Runtime 控制。

------

# 14. PredicateDefinition

Predicate 必须定义自己的逻辑约束。

例如：

```json
{
  "predicate_id": "leads",
  "roles": {
    "stock": {
      "type": "Stock",
      "cardinality": "1"
    },
    "theme": {
      "type": "Theme",
      "cardinality": "1"
    }
  },
  "directed": true,
  "transitive": false,
  "temporal": true,
  "required_evidence_grade": "B",
  "default_ttl": "PT4H"
}
```

还应支持：

```text
对称性
逆关系
基数
时态语义
Evidence要求
TTL
冲突策略
合并策略
允许推理来源
```

------

# 15. Ontology 生命周期

Schema 不采用简单：

```text
批准 / 不批准
```

二元模式。

使用：

```text
draft
  ↓
shadow
  ↓
active
  ↓
deprecated
```

------

## draft

AI 刚刚提出。

只允许研究。

------

## shadow

AI 已经可以实际使用这种类型进行实验。

但是：

> shadow Ontology 默认不得进入正式交易研判链。

这样 AI 可以自由探索：

```text
experimental://capital_cluster
experimental://benefit_transmission
```

而不会污染正式知识。

------

## active

正式 Ontology。

可以进入：

- M0；
- M1；
- M2；
- 正式查询；
- UI；
- 规则推理。

------

## deprecated

停止新增，但旧知识仍可历史读取。

------

# 16. Ontology Linter

系统必须检测 Ontology 膨胀。

新 Predicate 创建前检查：

```text
是否与已有 Predicate 高度相似
是否只是同义词
是否存在 inverse
domain/range 是否重复
transitive 声明是否合理
是否造成 Schema 循环
是否与现有 cardinality 冲突
是否产生无法满足的约束
```

发现问题后：

```text
quarantine
```

不能直接 active。

这可以避免几年以后出现：

```text
belongs_to
part_of
associated_with
related_to
linked_to
connected_to
```

大量语义几乎相同的关系。

------

# 17. KnowledgeChangeSet

所有 AI 对知识的修改统一通过：

```
KnowledgeChangeSet
```

禁止任何 AI 直接写数据库。

ChangeSet 至少包含：

```text
changeset_id
proposer
base_knowledge_seq
ontology_version
created_at
operations[]
reason
```

每个 operation 至少：

```text
op_id
op_type
expected_revision
payload
evidence_refs
as_of
confidence
reason
requested_policy
```

`op_id` 必须幂等。

同一个 op 重试不能产生重复知识。

------

# 18. 支持的 ChangeSet Operation

保持通用，而不是股票专用。

核心操作：

```text
define_entity_type
define_predicate

define_rule
define_view
define_procedure

upsert_entity

propose_statement
accept_statement
reject_statement
expire_statement
supersede_statement

bind_evidence

merge_entity

create_investigation_task
close_investigation_task
```

不要设计：

```text
create_theme_stock_relation
update_leader_stock
update_capital_flow
```

这种业务专用 API。

这些全部应该通过通用 Statement 表达。

# 19. KnowledgeService API

调用方只需要学习一组很小的接口。

核心 API：

```text

    -> KnowledgeSnapshot

    -> ValidationReport

commit(proposal_id, PolicyContext)
    -> CommitReceipt

maintain(MaintenanceSpec)
    -> MaintenanceResult
```

辅助 API：

```text
get_proposal_status()

list_open_questions()

list_conflicts()

get_statement_history()

explain_statement()

get_projection_status()
```

# 21. 权限与自动提交

使用风险分级。

------

## Level A：允许自动提交

例如：

```text
短期 Observation
有 TTL 的 hypothesis
确定性 derived Statement
已有 Ontology 内的低风险补充
重复 hypothesis 的置信度调整
自动 expiration
```

------

## Level B：需要 AI 复核

例如：

```text
hypothesis → evidence_backed 晋级
核心股票角色变化
跨周期结论
冲突消解
因果关系晋级
长期 Statement
```

可以由：

> 复盘 AI / Reviewer AI

进行语义复核。

但 Reviewer AI 仍然只能返回：

```
ReviewDecision
```

不能直接写数据库。

------

## Level C：必须人工确认

例如：

```text
Ontology active
Predicate 语义修改
Entity Merge
大范围失效
重要知识批量替换
交易规则变化
改变 Evidence 政策
改变自动提交权限
```

# 74. 最终架构一句话

整个系统最终可以概括为：

> **Immutable Change Log + Entity/Statement Knowledge Model + Versioned Ontology + Evidence/Temporal Governance + Justification Graph + Pluggable Projections。**

中文就是：

> 以 SQLite 追加式 ChangeSet 作为权威历史，以 Entity + Statement 作为统一知识模型，以版本化 Ontology 描述领域结构，以 Evidence、双时态和权限策略治理 AI 知识，以 Derivation Dependency 保存推理链，再通过可替换的 Graph/Search Projection 提供高效查询。

# 75. 最终目标

这个项目不是建设：

> Theme Graph。

不是建设：

> Stock Knowledge Graph。

甚至不是简单建设：

> Graph Database。

真正要建设的是：

> **AI-native Knowledge Runtime。**

它允许 AI：

```text
理解一个此前不存在的领域
↓
创建逻辑 Ontology
↓
识别 Entity
↓
提出 Statement
↓
建立假设
↓
寻找 Evidence
↓
发现潜在关系
↓
进行规则推理
↓
不断修正自己的知识
```

与此同时：

```text
Runtime
```

始终保证：

```text
AI不能越权
历史不可抹除
Evidence可追踪
未来数据不会泄漏到过去
事实与假设不会混淆
推理结果能够解释
Schema不会无限失控
正式研判能够完全复现
底层图数据库能够随时替换
```

因此最终职责边界是：

```text
AI
=
理解世界、提出知识

KnowledgeService
=
治理知识、保存历史

Projection
=
高效查询知识

人
=
制定规则、批准高风险变化
```

这就是本项目后续所有知识系统开发的最高层设计原则。
