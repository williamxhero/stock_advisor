会使用数据库，而且建议把“事实库”和“检索库”分开。

## 我的明确推荐

### 当前阶段

> SQLite + FTS5 + 结构化过滤

这是最适合当前单机、单用户应用的方案。

SQLite负责事务、版本、时点、引用关系和审计；FTS5负责关键词检索。[SQLite FTS5](https://www.sqlite.org/fts5.html)是SQLite自带的全文检索模块，不需要维护额外服务。

股票场景里很多最重要的检索条件本来就是结构化或精确词：

- 股票代码、名称；
- 题材和行业；
- 判断周期；
- 当时正确还是错误；
- M0/M1/H0；
- 日期和`known_at`；
- “弱转强”“冲高回落”“机器人链”等关键词。

这些信息使用SQLite过滤和全文检索，通常比一上来全部做向量检索更准确、更容易审计。

### 语义检索第二阶段

> SQLite作为事实源 + LanceDB作为可重建语义索引

当文章和历史判断积累到一定规模，或者检索评测发现“同一种意思、不同用词”经常召回不到，再接入LanceDB。

LanceDB适合本地嵌入式运行，并原生支持全文、向量和混合检索，可用RRF合并两种结果。[LanceDB混合检索文档](https://docs.lancedb.com/search/hybrid-search)

但LanceDB只能是派生索引：

```
SQLite权威记录
        ↓
文章切片与embedding
        ↓
LanceDB检索索引
```

LanceDB返回`record_id/revision`，runtime再回SQLite读取权威版本。向量库损坏或换embedding模型时，可以全部重建，不能反过来把向量库当事实源。

## 3. 文章建议怎么存

不要把所有网页直接塞进“记忆文本”。

建议分成三层：

```
原始文章
→ 规范化文章
→ 可重建检索切片
```

SQLite保存文章元数据：

- canonical URL；
- 标题、媒体和作者；
- 发布时间、获取时间；
- 股票、题材、政策等标签；
- 原始内容hash；
- 事实可靠性与市场传播程度；
- 是否被后续信息证伪；
- revision和有效状态。

较大的原始HTML、清洗正文可以按SHA-256保存为压缩内容文件，SQLite只保存路径和hash。文章切片、embedding和FTS索引都属于可删除、可重建的派生层。

## 4. 找回流程

建议采用混合召回，而不是只做向量相似度：

1. 强制`known_at <= 当前判断 as_of`；
2. 按股票、题材、周期和记录类型过滤；
3. FTS5找股票名称、专用术语和精确事件；
4. LanceDB找语义相近但措辞不同的经验；
5. 合并和重排；
6. 强制加入相关失败案例与最强反证；
7. 返回原始记录、来源、revision和当时验证状态。

例如查询：

> 机器人题材高开后分歧，现在是否还值得追？

系统不应只召回“机器人上涨”的相似文章，还应同时找到：

- 以前高开回落的失败判断；
- 当时被证伪的H0；
- 龙头上涨但跟随股退潮的案例；
- 当前证据与历史案例的关键差异。

## 最终选择

我推荐的顺序是：

```
第一阶段：
SQLite + FTS5 + 结构化标签

第二阶段：
SQLite + FTS5 + LanceDB混合检索

不推荐当前直接上：
独立Qdrant服务、纯向量库、Memory Palace或知识图谱
```

它们不是不能用，而是当前数据规模和单机应用还不足以抵消额外复杂度。最重要的不是先选最先进的“记忆库”，而是保证原文、时点、来源、错误观点和验证结果保存正确；检索技术以后可以替换。
